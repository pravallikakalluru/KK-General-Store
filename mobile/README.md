# GrocerEase — Mobile App (Flutter)

A Flutter (Android-target) ordering app for a grocery/general store, with two
roles sharing one login screen: **Owner** (catalog + order management) and
**Customer** (browse, cart, checkout, order history). Built against the
contract in `../docs/API_CONTRACT.md`.

## Current state of this folder

This folder was generated on a machine **without the Flutter SDK installed**,
so only hand-written Dart source exists:

```
mobile/
  pubspec.yaml
  lib/          <- complete, hand-crafted app source (see below)
  assets/
```

There is **no `android/` or `ios/` native wrapper yet** — those are
generated by the `flutter create` tool, which requires the Flutter SDK
(and for Android, the Android SDK/NDK), neither of which are available in
this environment. No `flutter`, `dart`, or `pub` command was run to produce
or validate this code — it was written directly by hand against the Flutter/
Dart APIs, so treat a first `flutter pub get` / `flutter analyze` as the
first real compile check.

## How to run this app

On a machine that **does** have the Flutter SDK and Android SDK installed:

1. **Add the missing native Android project** (non-destructive — this only
   fills in the platform folders Flutter needs; it does not touch the
   existing `lib/`, `pubspec.yaml`, or `assets/` you already have):

   ```bash
   cd mobile
   flutter create --platforms=android .
   ```

2. **Fetch dependencies:**

   ```bash
   flutter pub get
   ```

3. **Point the app at your backend.** Edit
   `lib/config/api_config.dart` and set `ApiConfig.baseUrl` (and
   `ApiConfig.hostRoot`, used to resolve relative `image_url`s returned by
   the API) to your running FastAPI backend, matching
   `API_CONTRACT.md` (`http://<host>:8000/api/v1`). Notes for local dev:
   - Android **emulator**: use `http://10.0.2.2:8000/api/v1` (this is the
     default already set in the file — `10.0.2.2` is the emulator's alias
     for your host machine's `localhost`).
   - Physical Android device on the same Wi-Fi: use your machine's LAN IP,
     e.g. `http://192.168.1.23:8000/api/v1`.

4. **Run it:**

   ```bash
   flutter run
   ```

## Architecture

- `lib/config/` — API base URL (`api_config.dart`), Material 3 theme/colors
  (`theme.dart`), and misc app-wide constants (`constants.dart`), including
  the forward-only order status transition map mirrored from the contract.
- `lib/models/` — `User`, `Category`, `Product`, `Order`, `OrderItem`,
  `CartItem`, and the `UserRole`/`OrderStatus` enums. Every model has
  `fromJson`/`toJson` matching `API_CONTRACT.md` field names exactly
  (snake_case on the wire, camelCase in Dart).
- `lib/services/` — one thin wrapper per API resource
  (`auth_service.dart`, `category_service.dart`, `product_service.dart`,
  `order_service.dart`, `notification_service.dart`), all built on the
  shared `api_client.dart` (a singleton `Dio` instance with the base URL
  and a request interceptor that reads the JWT from
  `flutter_secure_storage` and attaches
  `Authorization: Bearer <token>` to every call). `receipt_pdf_service.dart`
  is the **single shared PDF receipt builder** used by both the owner
  (`Printing.layoutPdf` → Android print dialog) and the customer
  (`Printing.sharePdf` → download/share) so the receipt layout only exists
  in one place. `whatsapp_service.dart` wraps `url_launcher` for opening
  the `whatsapp_url` returned by `POST /orders`.
- `lib/providers/` — `ChangeNotifier`-based state: `AuthProvider` (session +
  login/register/logout + startup session restore),
  `CartProvider` (in-memory, ephemeral per session), `ProductProvider`
  (full list + category/search-filtered view), `CategoryProvider`,
  `OrderProvider`, `NotificationProvider` (drives the owner's unread-count
  poll every ~15s per the contract). All registered via `MultiProvider` in
  `main.dart`.
- `lib/screens/auth/` — shared login/register screens; the role returned in
  `user.role` decides which shell `SplashScreen` (the root auth gate) routes
  to.
- `lib/screens/customer/` and `lib/screens/owner/` — each has its own
  bottom-nav shell (`customer_shell.dart`, `owner_shell.dart`) plus the
  screens listed in the spec (home/browse, product detail, cart, checkout,
  confirmation, order history/detail for customer; dashboard, categories +
  form, products + form, orders + detail for owner).
- `lib/widgets/` — reusable pieces shared across screens: `product_card`,
  `category_chip`, `cart_item_tile`, `order_status_badge` (used everywhere
  an order status appears), `primary_button`, `app_text_field`,
  `empty_state`, `loading_indicator`, `order_summary_card`,
  `quantity_stepper`.
- `lib/utils/error_handler.dart` — centralizes turning `DioException`s /
  the API's `{"detail": "..."}` shape (including FastAPI's 422 validation
  array shape) into a user-facing `SnackBar`, so screens just call
  `ErrorHandler.showError(context, e)` in a `catch` block instead of
  duplicating parsing logic. `lib/utils/formatters.dart` centralizes INR
  currency (`₹123.00`) and date formatting via `intl`.

## Notable implementation choices / deviations from the literal spec

- **`lib/utils/formatters.dart`** was added (not explicitly listed in the
  spec's folder sketch) to avoid duplicating `NumberFormat`/`DateFormat`
  setup across every widget/screen that shows a price or date — it's used
  by `receipt_pdf_service.dart`, `product_card.dart`, `cart_item_tile.dart`,
  `order_summary_card.dart`, and both order-detail screens.
- **`lib/screens/customer/customer_shell.dart`** and
  **`lib/screens/owner/owner_shell.dart`** were added to house the
  bottom-navigation shells described in the "Design" section of the spec.
  They weren't in the literal file-tree sketch but are necessary to
  implement "bottom navigation for the customer shell (Home / Cart /
  Orders / Profile) and for the owner shell (Dashboard / Products /
  Categories / Orders)".
- **`lib/screens/customer/profile_screen.dart`** was added since the
  customer bottom nav explicitly includes a "Profile" tab in the spec, but
  no dedicated screen file was listed for it. It shows the logged-in
  user's name/phone/email and a log-out action.
- **`lib/screens/splash_screen.dart`** was added as the root "auth gate" —
  it's what performs the "on app start, check secure storage... else show
  the login screen" flow described under "Auth persistence", and is set as
  `home:` in `main.dart`.
- The owner's order-detail screen class is named `OwnerOrderDetailScreen`
  (file `lib/screens/owner/order_detail_screen.dart`) to keep it distinct
  from the customer's `OrderDetailScreen`
  (`lib/screens/customer/order_detail_screen.dart`) — same filename in each
  role folder as specified, different class names since Dart doesn't allow
  two same-named top-level classes in the same import scope if a screen
  ever needed both (it doesn't currently, but this avoids the trap).
- The owner **Dashboard** screen (`lib/screens/owner/dashboard_screen.dart`)
  computes its stat tiles (pending/in-progress/completed order counts,
  product count, out-of-stock count) client-side from the same
  `GET /orders` and `GET /products` responses the Orders/Products screens
  already use, since `API_CONTRACT.md` defines no dedicated stats/reporting
  endpoint for the MVP.
- `pubspec.yaml` also declares `path_provider` (a transitive need of the
  `printing`/PDF sharing flow on some Android versions) even though it
  isn't explicitly listed in the spec's dependency list.
- Colors use the `Color.withOpacity(...)` API rather than the newer
  `Color.withValues(alpha: ...)` for broader compatibility with the
  `sdk: '>=3.3.0 <4.0.0'` constraint declared in `pubspec.yaml` — bump the
  Flutter/Dart SDK constraint if you want to migrate to `withValues`.

## Permissions (once you run `flutter create`)

After generating the `android/` folder, add these to
`android/app/src/main/AndroidManifest.xml` (inside `<manifest>`, before
`<application>`) so `image_picker`'s camera option and `printing`/file
sharing work correctly:

```xml
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.INTERNET" />
```

(`INTERNET` is usually present by default in a freshly generated project;
`CAMERA` is required specifically for the owner's "take a photo" product
image option.)
